01 · Where it started

It worked when there was one line

When the platform was only Marine, most clients worked the same way. Our admin set up each client and created every user from the backend. Any change followed the same loop.

How a change happened

  1. 1Client needs a change
  3. 2Contacts our admin
  5. 3Admin asks the backend team
  7. 4Backend makes the change
  9. 5Back to the client

Even adding one new user followed this loop.

02 · The problem

Manageable for one line. Not for five.

As new lines and clients arrived, each with its own roles and permissions, the loop could not keep up. Everyone felt it.

Clients

  • Even small changes, like a new user or a role tweak, meant contacting our admin.
  • Every client had its own roles and needed different permissions, but could not set any of them.
  • Waiting on us for minor changes made for a poor experience.

Our admin

  • Set up every client and created every user by hand.
  • Passed every role or permission request to the backend team, then back to the client.
  • The workload grew with every new line and every new client.

Backend team

  • Pulled into role and permission changes that should never have needed engineers.
  • Client-specific changes kept piling up in the queue.

What it added up to

The cost

Every client change became our work

The more lines and clients we added, the more our admin and backend team became a bottleneck, and the longer clients waited for simple changes.

03 · The goal

What the new module had to do

Before designing anything, I set four tests the module had to pass, one for each part of the problem.

1Clients change things themselves
A client's admin should add users and change roles or permissions without contacting us.
2Every client works their own way
Each client should name its own roles, set its own permissions and organise its own teams.
3No engineers in the loop
A user, role or permission change should never need backend work.
4One module for every line
The same module should work for every line of business and every client, without changes.
04 · The process

How I got there

First we worked out what the module had to contain. Then we made sure it worked for every line and every client.

The hard question

Could we ship a fixed set of default roles?

No. Fixed roles would never fit every line and every client. Each exception would send the client back to our admin, the same loop we set out to remove.

03 · The plan

One admin, then the client builds the rest

Instead of fixed roles, we built a flexible module. Each client designs its own setup inside it, and our team steps out after day one.

04 · The flow

Roles first, then users, then teams

I mapped the whole module as one flow. The order mattered: roles come first because they are assigned when a user is created, and teams are built from existing users.

05 · Admin levels

We had moved the bottleneck, not removed it

The module took the load off our admin and backend team. But it all landed on one client admin, and for clients working across many locations, that was too much for one person.

Who does what

  1. 1Super admin

    The first client admin, created by our team. Has every permission. Creates other admins and decides what each can do.

  2. 2Admins

    Created by the super admin, for a branch, a region or any split the client wants. Permissions are set by the super admin, up to full access.

  3. 3Team managers

    Run their own team with extra permissions, like managing members and assigning submissions.

  4. 4Team members

    Do the day-to-day work with the permissions their role gives them.

How the work is split is up to each client. We built the structure, and they decide how to use it.

Our admin, our backend team and now the client admin are all out of the bottleneck. Each client has a clear hierarchy, where everyone knows who does what.

05 · Edge cases

Thinking past the happy path

Before designing final screens, I walked through the first months of a client admin's life on the platform. At every awkward moment, I asked: what goes wrong here, and what should happen instead?

  1. Day oneNo roles yet
  2. Week one200 people
  3. Week twoSimilar roles
  4. Month twoSomeone leaves
  5. Month sixA restructure

An illustrative client admin's first months.

Day one

The admin wants to add people, but no roles exist yet

Without this

Nobody could be added until the whole role structure was designed. Onboarding would stall on day one.

What I designed

Every client starts with two roles, Admin and Member. New users become Members by default, so people can be added straight away and given custom roles later.

Principle

Never block the first day.

AMNew userMember

Week one

There are 200 people to add

Without this

Adding them one by one would take days, with a typo waiting in every form.

What I designed

Add users one by one, or in bulk. For bulk, the admin downloads a spreadsheet template, fills it in and uploads it.

Principle

Match the tool to the size of the job.

Week two

A new role is almost the same as an existing one

Without this

Every role built from scratch, one permission at a time, with small mistakes creeping in.

What I designed

Duplicate a role, rename it and remove a few permissions. Head of Underwriting becomes Senior, then Junior, in minutes.

Principle

Make the second time faster than the first.

What I designed

Their open work is never lost. If they were in a team, it goes to the team manager. If not, it goes to the admin, who reassigns it.

07 · My contribution

One flow I added that no one asked for

Inline reassignment on delete

Problem

Deleting a user blocked until their work was manually reassigned elsewhere. A broken, multi-step dead end.

Decision

Brought reassignment inside the delete flow. The system surfaces active submissions and prompts inline reassignment before confirming deletion.

Outcome

One guided flow handles both tasks, reassign and delete, without leaving the page.

08 · Results

Did it pass the four tests?

In section 03, I set four tests for the module. Here is how it did.

  1. Clients change things themselves

    Client admins now create users, roles, permissions and teams on their own. Our admin's job at onboarding shrank to one step: creating the client's first admin.

  2. Every client works their own way

    Clients name their own roles, split them into sub-roles, build teams by branch or region, and add more admins for their locations.

  3. No engineers in the loop

    Creating users, changing roles and permissions, and assigning teams used to be engineering tasks. Now they are settings the client controls. Tickets that still reach engineers are bugs, not setup requests.

  4. One module for every line

    The same module runs across all 5 lines of business, for every client.

09 · What this taught me

Designing generic systems is the hardest UX work

1

Generic systems need invisible flexibility

It has to work for every client without feeling built for someone else. That takes ruthless abstraction and thoughtful defaults.

2

Requirements don't design themselves

The inner details weren't in any brief. They came from understanding what a manager actually needs to do their job.

3

Critical flows must respect user intent

The admin wants to delete, so the flow helps them do it safely instead of standing in the way.

4

Data collected early pays dividends later

Region and country at creation felt minor. They became essential for smart team filtering down the line.

Systems design note

I designed this system so it would not need changing, however many new lines or clients join. For me, the real test of system design is how well it handles the cases you have not built yet.
