02

Findings

What we identified

Clients

"We have the system, but not the controls."

  • ✕

    Adding a new user

    Every new person meant a request to our admin team, and a wait.

  • ✕

    Removing a user

    When someone left, they had to ask us again.

  • ✕

    Roles and permissions

    Even one small permission change needed a request.

  • ✕

    Teams

    No teams in the platform. Everyone saw every submission and had to filter. They kept track of who was in which team in their heads.

  • ✕

    Locations

    No way to set up offices in different locations. Everyone saw everyone.

  • ✕

    Alerts

    After bind, everyone got everyone's alerts. Hundreds of them. Finding their own work was a real distraction.

Our admin team

More clients, more requests, more waiting

  • ✕

    More lines, more clients

    It was manageable with Marine alone. Now many lines of business and clients each worked their own way.

  • ✕

    More kinds of requests

    The number and types of requests kept growing, so things could easily be missed.

  • ✕

    Slow hand-offs

    Each request went from admin to developers and back. Clients had to follow up again and again.

Our developers

Basic client tasks became backend work

  • ✕

    Extra work every day

    Basic tasks clients should do themselves landed on top of their own work.

  • ✕

    Users and permissions in the backend

    Adding users, removing users and managing permissions were all done by hand.

  • ✕

    Big onboardings

    When a new client joined with many people, a lot of time was lost.

The real challenge

Every client has its own roles, rules and way of working. How do we design one common flow that works for all of them?

My contribution

One flow I added that no one asked for

Handing over work while deleting a user

Problem

An admin couldn't delete a user until someone moved their work by hand, somewhere else. It was a slow dead end with many steps.

Decision

I brought the handover inside the delete flow. The system shows the person's open requests and asks the admin to reassign each one before deleting.

Outcome

One guided flow handles both tasks, reassign and delete, without leaving the page.

Delete user · hand over open work

The handover lives inside the delete flow, so one action completes both tasks.

07 · What I learned

Notes I'm taking to the next platform

  1. Bend quietly for everyone

    One system should work for every client without feeling built for someone else.

  2. Briefs miss the details

    The inner details came from understanding what a manager really needs to do their job.

  3. Help, don't block

    The admin wants to delete, so the flow helps them do it safely.

  4. Ask early, use later

    Asking for region and country at sign-up felt minor. Later it let teams be filtered by location.

I designed this so it would not need changing, however many lines or clients join. The real test of a system is the cases you have not built yet.
